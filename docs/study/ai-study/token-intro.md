# Token 词元

当我们向 Deepseek、豆包、千问、ChatGPT 或 Claude 提问时，AI 是如何理解文字的？核心答案就是 Token（词元）这一概念。理解 Token 是进入 AI 世界的第一步。

---

## 什么是 Token（词元）？

Token（词元）是 AI 能够理解的最小文本单位，可以理解为"AI 世界里的文字碎片"或"AI 世界的燃料"。

类比人类阅读以词语为单位理解含义，AI 不会逐字母处理文字，而是先把文本切割成一块块碎片，每一块就是一个 Token。

### 示例

- 输入文本：`ChatGPT is amazing`
- 切分结果：`Chat` / `G` / `PT` / `is` / `amaz` / `ing`
- 共计 6 个 Token

### 比萨比喻

把文章想象成一块比萨，不会整块吞下，也不会碾成粉末，而是切成合适的块，每块就是一个 Token。Token 比单词更细，比字母更粗，是一种灵活的中间单位。

---

## Token 长什么样？

不同文本的切分方式差异很大。常见词通常是一个 Token，复杂词会被拆开，标点符号也算 Token。

### 英文句子示例

- 输入：`Hello, world!`
- 切分：`Hello` → `,` → `world` → `!`
- 共 4 个 Token

### 复杂英文单词示例

- 输入：`unbelievable`
- 切分：`un` / `believ` / `able`
- 共 3 个 Token（长词会被拆分）

### 中文句子示例

- 输入：`你好，世界！`
- 切分：`你好` / `，` / `世界` / `！`
- 共 4 个 Token（中文每字约消耗更多 Token）

---

## Token 和字、词有什么区别？

许多人会认为 Token 等于单词，但实际上并非如此。Token 的划分遵循特殊算法（如 BPE，字节对编码），结果有时直觉，有时出人意料。

### 文本与 Token 数量对照表

| 文本 | Token 数量 | 说明 |
|------|-----------|------|
| `cat` | 1 | 常见词，直接一个 Token |
| `unbelievable` | 4 | `un` + `believ` + `able` + ... |
| `ChatGPT` | 3 | `Chat` + `G` + `PT` |
| `你好` | 约 2~3 | 中文通常比英文消耗更多 Token |

### 三种粒度对比表

| 粒度层级 | 概念 | 粒度描述 | 示例 | AI 是否使用 | 类比 |
|----------|------|----------|------|-----------|------|
| 最细粒度 | 字符/字母 | 单个字母或汉字 | H, e, l, l, o | 太细，信息密度低 | 把比萨碾成粉末 |
| **AI 实际使用** | **Token（词元）** | 词根、短词、字符组合 | Hello / Chat·G·PT | 高效，平衡信息密度 | 把比萨切成合适的一口大小 |
| 最粗粒度 | 单词/句子 | 完整单词或句子 | Hello, unbelievable | 太粗，处理不灵活 | 整块比萨一口塞进去 |

## Token 为什么重要？

### 1. 决定了 AI 能读多少

每个 AI 模型都有一个**上下文窗口（Context Window）**，即一次能处理的最大 Token 数量。超过限制 AI 就会记不住之前的内容，类似短期记忆被填满。

各模型的上下文窗口示例：

| 模型 | 上下文窗口 |
|------|-----------|
| GPT-3.5 | 约 4,000 Token |
| GPT-4 Turbo | 约 128,000 Token |
| Claude 3.5 | 约 200,000 Token |

### 2. 影响 API 使用费用

调用 AI 接口（API）时，费用通常按 Token 数量计费。输入文字和 AI 回复文字都会消耗 Token，写得越长花费越多。

### 3. 影响 AI 的回复速度

AI 生成文字时是一个 Token 一个 Token 地输出，因此回复越长等待时间越久。

---

## Token 的小知识

- **1,000 个 Token 约等于 750 个英文单词**，是常用估算比例。
- **中文、日文、韩文**等亚洲语言通常比英文消耗更多 Token，因为编码上更复杂。
- **空格和标点**也算 Token，不只文字才计数。
- **代码**的 Token 消耗一般比自然语言少，因为编程语言结构紧凑。

---

## Token 计费模型

### 常见计费方式

| 计费项 | 说明 | 典型价格范围 |
|--------|------|-------------|
| 输入 Token（Prompt） | 用户发送的内容 | 较低 |
| 输出 Token（Completion） | AI 生成的回复 | 通常是输入的 2-3 倍 |
| 缓存命中 | 重复的前缀内容 | 通常有折扣 |

### 降低成本的技巧

1. **精简 Prompt**：去除冗余描述，保留核心指令
2. **限制输出长度**：在提示词中明确要求"不超过 X 字"
3. **使用缓存**：对重复的 System Prompt 利用 API 缓存机制
4. **选择合适的模型**：简单任务用小模型，复杂任务才用大模型

## Token 与上下文管理

### 上下文窗口的构成

上下文窗口中所有内容共享 Token 预算：

```
┌─────────────────────────────────────────┐
│           上下文窗口（Context Window）      │
│                                         │
│  ┌─────────────────────────────────┐    │
│  │ System Prompt（系统提示）         │    │
│  └─────────────────────────────────┘    │
│  ┌─────────────────────────────────┐    │
│  │ 对话历史（History Messages）      │    │
│  └─────────────────────────────────┘    │
│  ┌─────────────────────────────────┐    │
│  │ 当前用户输入（Current Input）     │    │
│  └─────────────────────────────────┘    │
│  ┌─────────────────────────────────┐    │
│  │ AI 输出（Response）              │    │
│  └─────────────────────────────────┘    │
│                                         │
│  所有部分共享同一个 Token 上限            │
└─────────────────────────────────────────┘
```

### 上下文溢出的后果

当对话内容超过上下文窗口限制时：

- 最早的消息会被截断或丢弃
- AI 会"遗忘"之前的对话内容
- 可能导致回答前后矛盾或丢失关键信息

### 管理上下文的策略

| 策略 | 做法 | 适用场景 |
|------|------|---------|
| 定期压缩 | 让 AI 总结之前的对话，用摘要替代原始消息 | 长对话 |
| 关键信息前置 | 把最重要的信息放在提示词开头或结尾 | 所有场景 |
| RAG 检索 | 不把所有文档塞进上下文，只检索相关片段 | 知识库问答 |
| 滑动窗口 | 只保留最近 N 轮对话，丢弃更早的消息 | 聊天机器人 |

---

## 总结

| 概念 | 一句话解释 |
|------|-----------|
| Token | AI 处理文本的最小单位，介于字符和单词之间 |
| 上下文窗口 | AI 一次能处理的最大 Token 数 |
| Token 计费 | API 调用按输入+输出的 Token 总量收费 |
| Token 生成 | AI 回复是逐 Token 产生的，越长越慢 |
| BPE 算法 | Token 切分的核心算法，字节对编码 |
| 估算比例 | 1,000 Token ≈ 750 英文单词 ≈ 500 中文汉字 |
