# 推理与规划（Reasoning & Planning）

在构建自主 AI Agent 的过程中，大语言模型相当于大脑，工具调用相当于手脚，而推理与规划则是将 Agent 从简单问答机升级为自主问题解决者的核心引擎。

复杂的现实任务往往无法通过一次生成完成，AI 需要具备拆解目标、逻辑推演、探索路径、自我修正以及调度工具的能力。以下是目前业界最主流的推理与规划框架。

---

## 思维链（Chain of Thought, CoT）

### 逐步推理能力

传统 LLM 生成答案时往往是直觉式的一步到位。CoT 的核心思想是强制要求模型在输出最终答案前，先显式地输出中间的推理步骤，这种做法能显著激活模型在复杂数学、逻辑推理和常识问答中的潜力。

CoT 不仅让模型有了更多的计算时间（token 数量代表计算量），还让后续的生成能建立在前面正确的逻辑基础上。

### 实例：Few-shot CoT 提示词设计

```python
# 通过提供包含推理过程的示例，引导模型进行 CoT 推理
prompt = """
问题：罗杰有5个网球。他又买了2罐网球。每罐有3个网球。他现在共有多少个网球？
解答：罗杰一开始有5个网球。2罐网球，每罐3个，共计 2 * 3 = 6 个网球。5 + 6 = 11。答案是11。

问题：食堂有23个苹果。如果他们用掉20个做午餐，又买了6个，现在有多少个苹果？
解答：食堂本来有23个苹果。用掉20个后剩下 23 - 20 = 3 个。又买了6个，现在有 3 + 6 = 9 个。答案是9。

问题：{user_question}
解答："""
```

## ReAct 框架（Reasoning + Acting）

### 推理 + 行动循环

如果说 CoT 只是在模型内部闭门造车，那么 ReAct 则是让模型睁开眼睛看世界。它将内部逻辑推理（Thought）与外部工具交互（Action）交织在一起，形成一个动态的闭环反馈系统。

在 ReAct 范式下，Agent 遵循 **Thought（思考）→ Action（行动）→ Observation（观察）** 的循环，直到得出最终结论。

### ReAct 循环流程

```
Thought: 分析当前状态，确定下一步需要什么信息
    ↓
Action: 调用外部工具（搜索、API、数据库等）
    ↓
Observation: 获取工具返回的结果
    ↓
Thought: 分析观察结果，判断是否足够回答问题
    ↓
（循环继续，直到得出最终结论）
```

### ReAct 示例

```
问题：2024年诺贝尔物理学奖得主是谁？他毕业于哪所大学？

Thought: 我需要查找2024年诺贝尔物理学奖得主的信息。
Action: search("2024年诺贝尔物理学奖得主")
Observation: 2024年诺贝尔物理学奖授予了 John Hopfield 和 Geoffrey Hinton。

Thought: 现在我需要查找 Geoffrey Hinton 毕业于哪所大学。
Action: search("Geoffrey Hinton 教育背景 毕业院校")
Observation: Geoffrey Hinton 于 1978 年在爱丁堡大学获得博士学位。

Answer: 2024年诺贝尔物理学奖得主之一 Geoffrey Hinton 毕业于爱丁堡大学（博士）。
```

> **局限性：** ReAct 在短期、步骤清晰的任务中表现优异，但由于整个思维和动作历史都积压在同一个上下文窗口中，当任务链条过长时，极易陷入死循环或因上下文超载而遗忘初始目标。

## Plan-and-Execute（规划先行执行模式）

为解决 ReAct 在长线任务中的不足，Plan-and-Execute 将思考和行动进行了解耦，采用类似人类做大型项目的策略：先出排期表，再挨个干活。

### 双角色架构

系统通常分为两个独立的角色：

1. **Planner（规划者）**：负责接收大目标，生成详细的 Step-by-Step 子任务列表。
2. **Executor（执行者）**：负责按顺序执行这些子任务。执行器通常就是一个小型的 ReAct Agent，每次只专注完成当前的一个小目标。

### 架构流程

```
复杂目标
    ↓
Planner 生成子任务列表：
  1. 抓取网页数据
  2. 提取关键信息
  3. 生成分析报告
    ↓
Executor 逐个处理子任务（每次独立上下文）
    ↓
最终交付
```

### Plan-and-Execute 的优势

| 优势 | 说明 |
|------|------|
| 上下文清晰 | 每个子任务使用独立上下文，不会累积过长 |
| 易于调试 | 可以定位到具体哪个子任务出了问题 |
| 适合长线任务 | 10步以上的复杂任务表现远优于 ReAct |
| 可人工干预 | 在 Planner 和 Executor 之间可以插入人工确认 |

## Tree of Thoughts (ToT) 与树状多路径探索

### 树状多路径探索

无论是 CoT 还是 Plan-and-Execute，本质上都是线性的路径探索。但在写代码、解数学题或创意写作时，人类往往会设想多种方案，评估后选择最佳的，甚至在发现错误时回溯。

ToT（思维树）将推理过程建模为一棵树：

- **节点**是当前的思维状态
- 模型会在每一个分支点生成**多个候选 Thought**
- 通过内部的 **Evaluator（评估器）** 对这些节点进行打分（如：可行、可能有风险、不可行）
- 结合 **BFS（广度优先搜索）** 或 **DFS（深度优先搜索）** 算法，决定是继续深入还是回溯重试

### ToT 搜索过程示意

```
                        [初始问题]
                       /     |     \
                 [方案A]  [方案B]  [方案C]
                 (可行)   (有风险)  (可行)
                /    \             /    \
           [A1]    [A2]        [C1]    [C2]
          (最优)   (一般)      (可行)   (不可行)
                      ↑                    |
                   回溯                   剪枝
```

## 任务规划 & MCTS（蒙特卡洛树搜索）

### 复杂任务拆解与搜索

在涉及战略游戏或极高难度的推理任务（如前沿的数学验证、复杂的代码仓库重构）时，简单的 ToT 仍不够高效。业界开始将 LLM 与传统的强化学习搜索算法 MCTS 结合（类似 AlphaGo 的核心逻辑）。

- **LLM 作为策略网络（Policy Network）**：提供启发式的下一步行动建议，减少无意义的分支扩展。
- **LLM/代码环境作为价值网络（Value Network）**：通过仿真执行（Rollout）预判某个行动序列的最终胜率或成功率。
- **优势**：在庞大的解空间中，能够找到最具有全局最优潜力的规划路径。

### MCTS 四步循环

| 步骤 | 名称 | 说明 |
|------|------|------|
| 1 | 选择（Selection） | 从根节点出发，按策略选择最有潜力的分支 |
| 2 | 扩展（Expansion） | 在选中的节点生成新的子节点 |
| 3 | 模拟（Simulation） | 从新节点开始随机 rollout 到终局 |
| 4 | 回溯（Backpropagation） | 将模拟结果反馈到路径上的所有节点 |

## Reflexion：自我反思与纠错

人类在执行任务时，如果第一次失败了，会总结经验教训并在下一次尝试中规避错误。Reflexion 框架赋予了 Agent 类似的能力。

### Reflexion 闭环机制

在 Reflexion 闭环中，当 Agent 的输出被判定为失败（例如：测试用例未通过、API 报错）时：

1. 触发一个 **Reviewer 机制**
2. LLM 被要求根据历史动作和失败的反馈写一段**口语化的反思**
3. 这段反思会被存入**情景记忆（Episodic Memory）**中
4. 作为下一次尝试的上下文提示，从而大幅提升 Agent 的自愈合能力

### Reflexion 工作流程

```
执行任务 → 失败 → 生成反思 → 存入记忆 → 再次执行（带反思上下文）→ 可能成功
                                          ↑                    |
                                          └── 再次失败 ────────┘
```

### 实例：Reflexion 的反思提示词设计

```python
reflection_prompt = """
你是一个正在尝试编写 Python 爬虫的 AI 助手。
这是你刚才执行的代码：{previous_code}
这是运行环境返回的错误信息：{error_traceback}

请深刻反思：
1. 错误发生的根本原因是什么？
2. 在下一次尝试中，你具体的修改策略是什么？

请将反思记录下来，以指导后续的行动。
"""
```

## 任务分解策略与工程化实践

在实际生产级的 AI 智能体开发中，纯靠 LLM "零样本"进行复杂规划是不稳定的。常用的混合干预策略包括：

| 干预策略 | 核心做法 | 适用场景 |
|---|---|---|
| **子任务模板化 (SOP)** | 预先定义好标准操作程序，让 LLM 在固定的状态机中流转 | 客服系统、标准化的数据清洗流水线 |
| **HITL (Human-in-the-Loop)** | Planner 生成任务列表后中断执行，要求人类用户确认、修改或审批后再执行 | 高风险操作：如删除数据库记录、发送群发邮件、大额资金转账 |
| **RLHF 引导规划** | 利用强化学习和人类偏好反馈，专门微调大模型的规划能力 | 底层大语言模型基座的训练阶段（如 OpenAI 的 o1 模型训练） |

## 框架对比总结

| 模式 | 核心机制 | 优点 | 缺点 |
|---|---|---|---|
| **CoT** | Step-by-Step 线性推理 | 实现极简，显著提升基础推理准确度 | 无法调用外部工具，容易一条道走到黑 |
| **ReAct** | 交替思考与行动闭环 | 动态适应环境，能通过观测实时调整 | 上下文容易随步骤累积而爆炸，迷失初衷 |
| **Plan-and-Execute** | 先拆解为子任务，再隔离执行 | 极其适合长线复杂任务，上下文清晰 | 面对突发变化（规划本身出错时）不够灵活 |
| **ToT / MCTS** | 树状搜索，评估回溯 | 能解决最高难度的复杂逻辑问题 | 计算成本极其高昂，Token 消耗呈指数级 |
| **Reflexion** | 基于失败反馈生成反思记忆 | 具备自我纠错和持续进化的能力 | 依赖明确的反馈信号（如代码编译器报错） |

---

## 如何选择合适的框架

| 场景 | 推荐框架 | 理由 |
|------|---------|------|
| 简单问答、数学题 | CoT | 实现简单，效果显著 |
| 需要联网或调用 API 的任务 | ReAct | 需要与外部环境交互 |
| 多步骤复杂任务（10步+） | Plan-and-Execute | 避免上下文爆炸 |
| 需要探索多种方案的任务 | ToT | 树状搜索找到最优解 |
| 代码生成、调试类任务 | Reflexion | 能从错误中学习 |
| 战略规划、博弈类任务 | MCTS | 全局最优搜索 |

---

## 总结

推理与规划是 AI Agent 从"能聊天"到"能做事"的关键能力跃迁。核心要点：

1. **CoT 是基础**：让模型"想清楚再说"，是最简单也最有效的推理提升技巧
2. **ReAct 让 AI 有了手脚**：通过工具调用与外部世界交互
3. **Plan-and-Execute 解决长线任务**：先规划再执行，避免上下文爆炸
4. **ToT/MCTS 处理高难度搜索**：树状探索在复杂解空间中找到最优路径
5. **Reflexion 赋予自我纠错能力**：从失败中学习，持续进化

在实际应用中，这些框架往往不是互斥的，而是可以组合使用——例如 Plan-and-Execute 中的 Executor 可以是一个 ReAct Agent，Reflexion 可以在 Plan-and-Execute 的基础上添加反思层。
